# Large BILL exports and weekly replacement

Date: October 19, 2026

Status: Approved for implementation planning on October 19, 2026. Implementation and live migration have not started.

## Purpose and agreed requirements

HWFC will continue downloading the original full Bills CSV through the same BILL export workflow and uploading it about once a week. The app must accept the larger historical export without requiring the user to edit, split, filter, or compress it manually.

Each successful export becomes the current comparison dataset. It replaces the previous active dataset rather than appending another week's copies of the same invoices. New statements compare with that current dataset. Existing PDFs, corrections, notes, stated reviewer initials, completed reviews, and historical evidence remain available.

This changes importing and retrieving BILL comparison data inside the HWFC app. It does not write invoices, payments, or journal entries to BILL or QuickBooks. Daily Deposits, Credit Cards, PDF extraction, and the shared-password access model remain outside this change.

## Observed size and existing constraints

The supplied October 19 export contains 284,365 CSV source rows. The current native importer produces 223,425 comparison records after safely consolidating 59,592 line-item rows and excluding 1,348 rows under its existing rules. Its raw size is 155,585,995 bytes. A read-only streaming gzip measurement produced 14,312,222 compressed bytes, preserving the complete original file.

The previous export contained 7,093 source rows and produced 5,610 comparison records. The new export contains invoice dates from 2014 onward; the previous file predominantly contained 2026 invoices. The larger count is not simply an extra week's purchases.

Current browser, Python, repository, and SQL checks enforce 100,000 records and 20 MiB per original file. Opening AP also downloads every active BILL record into the browser. Increasing those constants alone would leave excessive memory, transfer, and repeated database-storage costs.

These figures are local diagnostic results, not measurements of current Supabase account usage. Private source files and their contents must not be committed to Git or uploaded during development.

## Selected architecture and alternatives

Use immutable, compressed BILL snapshots in the existing private Supabase bucket. Store only import metadata and the active snapshot pointer in Postgres for new imports. A snapshot consists of the losslessly compressed original CSV and a compressed, indexed SQLite comparison file generated by the Python server. SQLite is a derived search index, not a new hosted service. Python's standard library supplies SQLite, CSV parsing, hashing, and gzip support.

The server opens a verified local copy of the index read-only and returns only records needed for the current statement. The browser retains the existing matching and evidence rules, with a complete vendor directory and explicitly complete candidate sets instead of the full historical dataset.

This approach avoids adding hundreds of thousands of Postgres rows for every weekly full export. The alternatives are retaining the existing row-per-import architecture with larger quotas, which does not address browser loading or weekly growth, or requiring filtered exports, which conflicts with the accepted workflow and can omit older invoices. A paid plan is not a prerequisite to implementation, but continued free operation depends on measured total storage and transfer usage.

## Weekly replacement and duplicate prevention

There is exactly one active BILL import per workspace. Current searches query only that import. They never union current and historical imports.

A SHA-256 hash of the decompressed original bytes identifies an export, independently of its filename or gzip encoding. Re-uploading identical bytes, including a renamed file, reuses the existing import and its artifacts. Retries reuse operation identities and cannot create a second import or activate a partially built one. Re-uploading the already active file reports that the data is already current. If the identical file belongs to an older saved snapshot, request confirmation before making it current again; a duplicate upload must not silently roll the workspace back.

An updated full export creates a new snapshot. Invoices already present in that file are not appended to the previous active list. Changed status or amounts come from the new snapshot, and newly exported invoices become available. An invoice omitted from the new file is absent from current comparisons; the app must not silently mix an older version into the current dataset.

Repeated CSV rows within one export still use the current conservative consolidation rules. Combine line items only when vendor/reference/date grouping, bill-level fields, line counts, zero-based order, and line-amount sums establish one consistent bill. Equal amounts or invoice references alone do not justify removing rows. Ambiguous duplicates supplied by BILL remain review evidence, not an automatically selected or discarded invoice.

Historical snapshots are retained versions of evidence, not additional current invoice entries. They can contain the same invoice in different weeks. The UI must explain this distinction without claiming that immutable history consumes no storage.

## Import flow

1. The existing Update BILL data tutorial and file chooser remain the entry point. Selecting the original CSV starts a dedicated Web Worker that streams it through gzip. Do not run the old whole-file CSV parser or create a full normalized-record array in the main browser thread.
2. Upload compressed bytes through a new BILL-specific, authenticated chunk contract. Keep PDF uploads and their 20 MiB limit unchanged. Show Preparing file, Uploading, Checking records, and Saving as distinct states. Do not display Saved until activation is acknowledged.
3. Python verifies each uploaded chunk and the assembled compressed file. It streams decompression to a private temporary file, enforces decompressed size and CSV structural limits, computes the original hash, and checks for an existing import before building another index.
4. A disk-backed builder stages parsed rows in SQLite, validates native headers and values, and processes invoice groups without retaining the entire export in memory. It produces the same normalized fields, warnings, source row numbers, and grouping results as the current JavaScript importer. Preserve the existing app-template CSV format as well as native BILL exports. Monetary values use exact integer cents, invoice references remain text, and missing or invalid amounts never become zero.
5. Complete the build, close the writable index, verify counts and integrity, then gzip and upload the index. Both artifacts use immutable, server-generated paths and verified hashes. No browser-provided SQLite database is accepted.
6. Save the validated snapshot manifest and atomically switch the active import. A compare-and-swap check against a monotonically increasing workspace import version captured at the start prevents two concurrent updates from silently replacing each other, including a source that changed and was later restored. A conflict keeps the existing active source and offers an explicit retry.
7. Refresh source metadata and invalidate current candidate caches. New statements use the acknowledged import. Existing drafts retain their corrections and notes; comparing a draft against the new source requires a visible refresh and fresh review decisions. Completed revisions retain their original results and source references.

Compression is an internal transport detail. Users continue choosing the original CSV, not a gzip or SQLite file. Browsers without the required streaming compression support receive an actionable compatibility message rather than a memory-heavy fallback.

## Bounded processing and recovery

New snapshot imports accept up to 256 MiB of original CSV, 32 MiB of compressed CSV, 750,000 source rows, and 500,000 normalized records. Each index archive is limited to 32 MiB and its expanded index to 512 MiB. Reject oversized input clearly and before activation; never truncate a source or import only the first allowed records. Existing small import and PDF paths retain their current limits.

Retain 256 KiB transport chunks and the existing 1 MiB component envelope. Stage keys allow indexes through the full compressed-file range instead of the current two-digit index restriction. Limit CSV input to 128 columns and 1 MiB per field. A limit violation is an explicit import failure, not a skipped row.

Build work runs through sequential, bounded server steps, not one unbounded component request. A build handle is tied to workspace, authorized session, original hash, and generation. Each step consumes at most 5,000 source rows or 500 invoice groups, with a five-second cooperative time budget. A repeated step with the same expected checkpoint returns its acknowledgement without processing those rows twice. Complete oversized groups through resumable row iteration; never split one group into falsely independent bills.

The compressed original is durable before building starts. Intermediate build files and handles are private, process-local temporary state. If the process restarts or those files expire, return Restart required and rebuild from the saved original under a new generation. Do not claim that an expired local checkpoint has resumed. The last successful dataset remains active throughout. Upload failures retain verified staged chunks for an in-session retry; finishing an already acknowledged operation remains idempotent.

Bound simultaneous builds to one per workspace through an expiring server-owned database lease and two per server process. Expire abandoned temporary builds after one hour. Release file handles before cleanup. Cleanup of this application-owned temporary state must not remove any Supabase originals, completed snapshots, statement PDFs, or review history.

After a complete compressed original is durably verified and its upload state is acknowledged, remove only that upload's server-generated staging chunks. Before each deletion, check workspace, upload ID, stored chunk hash, and the exact staging-key allowlist. Never infer a broad directory or delete final artifact keys. A lost cleanup acknowledgement can retry exact keys safely. Failed or abandoned staging objects remain until an administrator uses the existing separately authorized cleanup procedure; account for them in storage estimates.

## Snapshot manifest and schema

Add a new migration without editing the deployed migration. Extend import metadata with a storage format, parser/index version, original hash and byte count, compressed artifact paths and hashes, expanded index size, source and normalized row counts, exclusion/consolidation counts, warning count, optional snapshot date, and a vendor-directory digest. Add the workspace import-version counter and expiring build-lease metadata used for concurrency checks.

Preserve existing imports as rows-v1. New imports use snapshot-v2. Apply the larger record-count constraint only to snapshot-v2; legacy append-record operations cannot populate or activate a snapshot-v2 import. Snapshot activation requires a server-verified manifest, both complete artifacts, the expected prior active source, and matching counts. Preserve the existing workspace/hash uniqueness and immutable-history protections.

The index has normalized records with stable source ordinals, vendor lookup keys, invoice lookup keys, transaction kinds, amounts in cents, and the existing evidence fields. Add indexes for reference/kind and vendor/kind/amount. Preserve original display values separately from lookup keys. Keep a distinct vendor directory and import warnings in the same index. Do not write these normalized rows into ap_bill_records for snapshot-v2.

Record IDs remain import-scoped and stable, using the existing import-ID/ordinal convention. Store source row provenance even for safely consolidated records. Details of all exclusions and source warnings remain available through paginated import details, rather than embedding hundreds of thousands of entries in a bridge response or Postgres metadata row.

## Retrieving comparison data

Bootstrap returns active metadata and a paginated vendor directory, not every BILL record. Vendor identity uses the complete directory and the current normalization and mapping rules. A partial directory must never establish a unique vendor.

Add an allowlisted comparison-record query accepting an import ID, bounded lists of statement references/kinds and vendor/amount/kind keys, and an opaque cursor. It accepts no SQL, object path, URL, or workspace selector. Python uses parameterized read-only queries and validates every returned record.

Retrieve exact-reference candidates across vendors first, along with same-vendor candidates needed by the existing fallback rules. Amount searches stay within a confirmed vendor. Preserve a reference disagreement as an exception; another invoice with the expected amount cannot replace it automatically. Return all relevant duplicates, not a first match. An unresolved vendor or equal-amount ambiguity stays visible for user review.

Responses identify the pinned import, query digest, full candidate count, page order, and next cursor. Page by at most 500 records and by the serialized envelope size, whichever is smaller. Assemble a complete candidate set before applying a unique-match or missing conclusion. A missing page, import mismatch, cache miss, or unavailable index means comparison unavailable, never invoice not found. Extremely large candidate sets remain paginated review evidence with no automatic unique match.

Cache candidate results by import ID, statement comparison inputs, mappings, and rule version. Editing a reference, amount, vendor, transaction kind, or mapping invalidates the affected result. Saving or marking reviewed must await an acknowledged comparison against one pinned source. Pending requests and old responses cannot overwrite a newer edit.

Support rows-v1 through the same candidate-query interface, using validated Postgres queries or the existing paginated reader internally. Existing imports and completed history must work without an automatic migration or re-upload.

## Server cache and security

Download snapshot indexes only after authorization and private-bucket checks. Verify compressed and expanded hashes and size bounds, then open SQLite in read-only mode with extensions disabled and no user-defined SQL. Only server-generated index schemas are accepted. Reject unsupported schema versions and failed integrity checks.

Cache verified files by workspace, import ID, and manifest digest in private temporary directories. Enforce a 512 MiB total expanded-index cache budget with least-recently-used eviction, reference-counted readers, and a one-hour idle expiry. Cached financial data never bypasses authorization. A cache loss only requires a verified download, not a new user upload.

Supabase credentials stay in Streamlit Secrets and never enter browser code, workers, manifests, logs, or signed URLs. Preserve existing access expiry, password rotation, mutation revalidation, private object access, revision version checks, optional notes, and required reviewer initials. Logs contain sanitized operation identifiers, counts, timings, and sizes only.

## Storage cost and retention

On October 19, the published Supabase Free limits are 500 MB of database storage, 1 GB of file storage, and 50 MB per file. The measured compressed original is below the per-file limit, but that alone does not establish that the complete workspace or repeated weekly archives fit the free tier. The actual index size, existing PDF usage, historical snapshots, and transfer usage must be measured before enabling the feature in production.

Reuse identical artifacts and imports. Do not retain a second uncompressed original in Supabase, write a second full set of normalized records to Postgres, or silently discard old files to make room. Record artifact sizes in the manifest and show a storage warning at 80% of the configured workspace budget. Reserve space for staging plus final artifacts before writing; use a conservative configured bucket budget of 900,000,000 bytes until the administrator supplies another budget. Treat quota errors as Not saved and leave the prior source active.

Account-wide usage can include data outside this app, so the reservation is not a guarantee of remaining quota. Configuration and deployment checks must include current Supabase usage. No paid-plan switch, charge authorization, automatic retention deletion, or promise of unlimited free history is part of this feature. If capacity becomes insufficient, request a separate decision about retention, capacity, or a paid plan.

## User interface

Keep Update BILL data as one tutorial followed by one original-CSV selection. Show progress, source-row versus comparison-record counts, and a plain success message: BILL data updated. Previous invoices were refreshed, not added again. A byte-identical re-upload instead says This export is already saved and whether it is already current.

Show the current export filename, import time, optional snapshot date, and record count. Keep technical warnings and storage information under BILL data details. A failed update states the specific failed stage and confirms that the previous dataset remains current. Retry never resets statement work. Do not show a success count until the server has acknowledged activation.

## Validation and rollout

Implementation must include automated tests for these requirements:

- Parser parity with the existing native-import tests, including signed lines, zero-based orders, missing amounts, different dates, duplicate bills, currency limitations, exclusions, and conflicting bill fields. Cross-language normalization tests cover invoice suffixes, leading zeros, vendor punctuation, Unicode normalization, date parsing, and exact decimal-to-cent conversion.
- Large synthetic exports above 100,000 and 223,425 normalized records, with measured memory use. The builder must not retain all source rows or records in Python or browser memory. Target a server peak RSS increase below 256 MiB for a fixture of the supplied size and bounded browser buffers independent of original CSV size.
- Identical files with changed names or gzip headers, duplicate clicks, lost acknowledgements, interrupted uploads, process restarts during builds, two concurrent updates, and retries after successful activation. None may duplicate active invoice entries or switch to an incomplete source.
- Weekly replacement with old invoices, new invoices, changed fields, and omitted invoices. Compare only the selected snapshot and retain historical evidence separately. Never append old snapshots into current matching.
- Candidate pagination beyond service defaults, complete vendor resolution, invoice-first matching, exact-reference amount differences, same-vendor amount-only suggestions, multiple candidates, stale responses, edited statement inputs, missing pages, and unavailable or corrupt indexes.
- Access rejection, expiry and rotation, forged build handles, arbitrary paths and SQL, compressed-size and expansion limits, chunk indexes beyond 99, CSV structure limits, oversized warnings, quota failures, cache isolation and eviction, and no secrets in frontend assets or logs.
- Existing saved imports, PDFs, notes, initials, statement corrections, completed revisions, historical comparisons, and review conflict behavior. Existing application regression suites remain required.

After implementation, inspect the real supplied CSV locally without logging record contents. Verify parity with the established source/consolidation/exclusion/record counts, archive round-trip hashes, candidate-query results, index size, processing duration, and memory. Do not upload that file to live storage merely to run a test.

Roll out the additive schema and private-bucket MIME/size configuration to a user-approved test environment first. Test with synthetic financial data, including two independent sessions and a server restart. Verify compatibility before enabling the new UI. Merging, pushing, applying a live migration, and replacing the real active dataset remain explicit later actions. Do not drop legacy tables or delete prior imports during rollout.
